# V1 轻量设计包

## 1. 项目定位

### 1.1 一句话定位

一个面向泛技术爱好者的轻量技术创作社区，强调技术内容发布、个人创作管理、问题解决方案沉淀与轻量讨论。

### 1.2 V1 产品目标

- 先建立稳定的内容发布主链路
- 让用户可以沉淀自己的技术博客、算法题解、踩坑记录和工具体验
- 通过个人中心管理创作状态，而不是先做强社交互动
- 具备最小的后台治理能力：帖子审核、分区管理、精选内容审核

### 1.3 V1 不追求的目标

- 不追求大而全社交能力
- 不优先做点赞、收藏、关注、通知等强互动模块
- 不追求复杂后台和大盘统计

---

## 2. 内容架构决策

## 2.1 V1 采用一级分区 + 标签体系

### 决策

V1 不做数据库层面的二级分区，采用：

- 一级分区：承担社区主导航与内容大类归档
- 标签：承担细粒度主题描述与内容筛选

### 原因

- 当前数据库和接口都是围绕单层分区设计的，直接改成二级分区会牵动查询、后台管理、前端导航和数据迁移
- 你的项目当前更需要快速形成稳定的内容组织方式，而不是提前上复杂层级结构
- 对于学生作品集项目，一级分区 + 标签已经足够专业，也更容易讲清楚产品取舍

### 未来扩展

如果后期确实需要二级分区，推荐在 `categories` 表增加 `parent_id` 实现树形层级，而不是用状态字段去区分分区层级。

### 明确不推荐

- 不推荐用 `status` 表示一级/二级分区
- 不推荐把分区层级编码进帖子状态或其他业务字段

---

## 2.3 标签体系

### 标签定位

标签用于描述帖子具体主题、技术方向、场景或特性。

例如：

- Java
- Python
- Linux
- Redis
- LeetCode
- 蓝桥杯
- AI资讯
- Prompt
- 部署
- 排错

### 标签设计原则

- 一个帖子可以关联多个标签
- 标签比一级分区更细粒度
- 标签用于筛选、搜索和作者技术方向展示

### 标签数据模型建议

采用标准多对多设计：

- `tags`
- `post_tags`

不建议把标签列表字符串直接作为事实来源存进 `posts` 表。

### 最佳实践建议

- **事实来源**：`tags` + `post_tags`
- **查询展示**：通过关联查询或按帖子 ID 批量查询标签
- **性能优化**：如果后期列表性能有压力，再考虑增加冗余字段或缓存，而不是一开始就做双写结构

### 当前阶段结论

V1 先按标准关系型设计实现，避免过早优化。

## 3. 首页设计

## 3.1 首页目标

- 让用户快速看到社区最新内容
- 让用户快速发现高质量解决方案
- 让用户可以按标签和分区筛选内容

## 3.2 首页主结构

### 顶部区域

- Logo / 产品名
- 搜索框（先保留入口，可后续实现）
- 发帖入口
- 登录 / 用户入口

### 左侧区域

- 主分区导航

### 中间主区域

- Tab 1：最新发布
- Tab 2：精选方案
- 帖子列表

### 右侧区域

- 热门标签
- 创作者入口 / 个人中心入口

---

## 3.3 首页帖子卡片字段

每张卡片建议展示：

- 标题
- 分区
- 摘要
- 作者
- 最近活动时间
- 浏览量
- 评论数

### 最近活动时间定义

首页列表排序不再只依赖 `update_time`，而是建议引入 `last_activity_time` 概念。

推荐定义：

- 有最新评论时：取最新评论时间
- 没有评论时：取帖子创建时间

### 排序规则

- 默认按 `last_activity_time DESC`

### 原因

- 更符合社区使用习惯
- 比单纯按创建时间更有活跃感
- 比滥用 `update_time` 更清晰，因为 `update_time` 应代表内容编辑时间

---

## 3.4 精选方案机制

### 目标

突出高质量的解决方案型内容，增强内容沉淀属性。

### 规则

- 只有已发布帖子可以申请精选
- 作者在个人中心“我的已发布帖子”发起申请
- 管理员在后台审核是否进入精选

### 第一版实现建议

- 帖子增加 `is_featured` 标识
- 是否展示在精选页由管理员审核结果决定

后期如果要更细致，再加“精选申请状态”。

---

## 4. 发帖与状态流设计

## 4.1 发帖页核心操作

- 保存草稿
- 发布帖子

### 用户心智

用户看到的动作只有：

- 保存草稿
- 发布帖子

系统内部根据审核开关决定真实状态。

---

## 4.2 帖子状态定义

- `0 DRAFT`：草稿
- `1 PENDING_REVIEW`：待审核
- `2 PUBLISHED`：已发布
- `3 REJECTED`：已拒绝
- `4 DELETED`：已删除

---

## 4.3 状态流转规则

### 保存草稿

- 创建或更新后状态保持为 `DRAFT`

### 发布帖子

- 审核关闭：进入 `PUBLISHED`
- 审核开启：进入 `PENDING_REVIEW`

### 审核通过

- `PENDING_REVIEW -> PUBLISHED`

### 审核拒绝

- `PENDING_REVIEW -> REJECTED`

### 被拒后重新编辑再发布

- 审核关闭：进入 `PUBLISHED`
- 审核开启：重新进入 `PENDING_REVIEW`

### 删除帖子

- 作者删除：进入 `DELETED`

---

## 4.4 审核开关设计

第一版仅做全局开关：

- `review.enabled = true / false`

### 含义

- `false`：发布即公开
- `true`：发布进入待审核

### 说明

V1 不做分区级审核策略，避免增加过多复杂性。

---

## 4.5 摘要策略

### 决策

- 摘要保留
- 摘要长度上限：300 字

### 体验建议

- 用户可以手动填写摘要
- 如果未填写，后端自动从正文提取默认摘要

这样可以兼顾可控性与易用性。

## 6. 数据模型升级建议

## 6.1 建议新增或调整字段

### `posts`

建议增加：

- `last_activity_time`
- `is_featured`

说明：

- `last_activity_time`：用于首页排序和社区活跃度表达
- `is_featured`：用于精选内容展示

### `tags`

建议新增：

- `id`
- `name`
- `slug`（可选）
- `use_count`（可选）

### `post_tags`

建议新增：

- `post_id`
- `tag_id`

### 浏览足迹

如果 V1 要落地“我的足迹”，建议新建：

- `user_browsing_history`

核心字段可为：

- `user_id`
- `post_id`
- `last_view_time`

如果时间紧，可放到 V1.1。

---

## 6.2 标签查询实践建议

### 最佳实践结论

- 不建议在 `posts` 表额外保存“标签列表字段”作为事实来源
- 标签事实来源应保持在关联表中

### 原因

- 避免双写不一致
- 避免更新标签时同步困难
- 关系型数据库处理多对多关系天然适合使用中间表

### 如果后期有性能需求

可以增加：

- 缓存
- 查询结果组装
- 视图对象层面的标签摘要字段

而不是直接让冗余字段承担唯一事实来源。

## 7. 接口设计建议

## 7.1 推荐接口语义

### 创建草稿

- `POST /api/posts`

行为：

- 创建一篇新帖子
- 默认进入 `DRAFT`

### 更新帖子 / 自动保存

- `PATCH /api/posts/{id}`

行为：

- 草稿编辑
- 自动保存与手动保存共用

### 发布帖子

- `POST /api/posts/{id}/publish`

行为：

- 根据审核开关决定进入 `PENDING_REVIEW` 还是 `PUBLISHED`

### 申请精选

- `POST /api/posts/{id}/feature-request`

行为：

- 作者对已发布帖子发起精选申请

### 审核精选

- `POST /api/admin/posts/{id}/feature`

行为：

- 管理员批准或拒绝精选申请

---

## 7.2 为什么推荐“草稿 + 发布动作”分离

### 原因

- 更符合用户心智
- 更符合内容系统的状态流设计
- 更适合自动保存
- 更容易把“保存”和“发布”做成两个清晰动作

### 推荐实现方式

- 自动保存和手动保存都走更新接口
- 发布独立成动作接口，由后端接管状态转换逻辑

这比让前端直接传最终状态更合理。
