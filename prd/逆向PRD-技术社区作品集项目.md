# 逆向 PRD：技术社区作品集项目

## 1. 文档说明

本文档不是从零规划出来的 PRD，而是基于现有仓库中的以下证据逆向整理出的产品前期文档底稿：

- 现有后端代码与数据库结构
- 现有前端页面与路由
- Git 提交记录与开发日志
- 旧版 SRS / SDD / 原型 HTML / API 文档

因此本文档分为两类内容：

- **已验证**：能被当前代码、数据库或接口直接证明
- **待你验证**：从原型、旧文档或代码意图推测出的需求，当前未形成稳定闭环

本文档目标不是“还原历史真相”，而是把项目重构为一份**可以用于实习作品集表达**的、足够可信的产品与需求说明。

---

## 2. 项目定位

### 2.1 一句话定位

一个面向技术学习与经验分享的轻量级社区论坛，支持用户注册登录、发帖、评论、分区浏览、图片上传与基础内容审核。

### 2.2 作品集表达版定位

这是一个由我独立主导开发的全栈社区项目，重点展示：

- 账号体系与权限控制
- 内容型产品的核心业务链路
- 面向真实场景的后端工程设计
- 从需求、接口、数据结构到页面交互的完整思考

### 2.3 产品边界判断

结合当前代码和数据，本项目更适合作为：

- **带审核能力的技术社区作品集项目**

而不是：

- 大而全的综合社交平台
- 强社区关系链产品
- 重推荐、重消息系统的平台型产品

---

## 3. 产品目标

### 3.1 核心目标

- 让用户可以围绕技术主题进行发帖、浏览、评论和交流
- 让内容按分区组织，降低信息混乱度
- 让社区具备最基础的治理能力，如帖子状态管理、管理员审核、分区管理

### 3.2 作品集目标

- 展示完整的 Web 产品主链路，而不是零散功能点
- 展示后端架构能力，而不只是 CRUD
- 展示我能从需求、设计到实现推进一个中等复杂度项目

### 3.3 非目标

以下方向从现状看不应作为当前阶段主目标：

- 推荐算法
- 即时聊天
- 完整消息中心
- 复杂举报与风控体系
- 商业化变现体系

## 8. 关键业务规则

### 8.1 认证与权限规则

- 未登录用户只能访问公开内容
- 发帖、评论、上传头像等操作必须登录后进行
- 用户只能修改或删除自己的帖子
- 用户只能删除自己的评论
- 管理接口必须限制为管理员访问

### 8.2 帖子状态规则

当前代码已体现 5 种状态：

- `0` 草稿
- `1` 待审核
- `2` 已发布
- `3` 已拒绝
- `4` 已删除

推测状态流转为：

- 发帖后进入草稿或待审核
- 管理员审核后发布或拒绝
- 作者删除后进入软删除

其中“默认进入草稿还是待审核”需你再确认，因为当前代码和原型可能存在阶段差异。

### 8.3 分区规则

- 分区有启用/停用状态
- 游客与普通用户只能看到启用分区
- 管理员可以看到全部分区并进行管理

### 8.4 图片资源规则（待你验证）

大概率原本想设计为：

- 上传图片时先进入临时资源池
- 发帖成功后将临时图片绑定到帖子
- 失效的临时图片由系统清理

这是一个很适合做作品集亮点的资源治理机制。

## 13. 对外包装建议：突出业务还是技术栈

## 13.1 结论

**建议：以业务主线为外壳，以技术实现为亮点。**

不要把项目包装成“我用了很多技术栈”，而要包装成：

- 我做了一个有完整用户链路和内容治理思路的技术社区项目
- 为支撑这条业务链路，我做了权限、状态、分页、上传、缓存、异常、对象存储等工程设计

### 13.2 为什么不能只突出技术栈

如果只强调技术栈，项目会变成：

- Spring Boot
- Spring Security
- Redis
- MinIO
- Vue
- MyBatis

这会很像“课程拼装项目”，缺少产品思考和业务组织能力。

### 13.3 为什么也不能只讲业务

如果只讲业务，会显得项目深度不够，因为你的真正优势在后端工程实现已经有不少内容。

### 13.4 推荐表达方式

建议简历和面试中采用以下结构：

1. **先说产品**：做了一个技术社区项目，核心解决内容发布、组织和基础治理问题。
2. **再说场景**：有游客、用户、管理员三类角色，围绕注册登录、发帖评论、分区管理和内容审核形成主流程。
3. **最后说技术**：为了保证系统可用性和可扩展性，引入 JWT 鉴权、Redis、MinIO、状态管理、分页和统一异常机制。
